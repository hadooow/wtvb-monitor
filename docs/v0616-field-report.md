# v0.6.16 内置蓝牙连接恢复（2026-10-03）

## 日志证据

依据用户提供的 `WTVB-diagnostics-v0.6.15.zip`，只读取诊断和运行日志。

- 12:29:01–12:29:29 五台均发现 FFE5/FFE4 并收到有效样本。
- 12:29:55–12:33:36 连续多轮手动断开/重连成功，因此不能声称上一版完全无法重连。
- 12:42:34 并发数从五台改为三台，登记设备仍为五台，开始自动轮换。
- 12:48:27 FE6 首次返回 `gatt []`，随后 C5AE、D60、E95、D169 都出现相同失败。至 13:03:33 共 14 次 `connect_failed`，阶段均为 `service_and_characteristic_check`，原因为 FFE5/FFE4 缺失。并非 14 次 `TimeoutError`。
- 服务缺失后仍调用 `stop_notify`，附带“Characteristic ... was not found”错误。诊断结束时仅一台在线。

日志确认服务枚举失效，但无法独立判定 Windows 驱动、其他客户端占用或传感器端状态中的唯一根因。自动轮换频繁创建会话与失败时使用同一查询方式是本版重点修正的路径。

## 处理

1. 仍优先对 FFE5 非缓存定向查询。返回空服务、缺少 FFE4 或通知属性时，记录 `service_recovery`；完成释放，冷却 10 秒并重新发现，下一次对该设备使用完整非缓存查询，成功后本次运行保留该方式。完整查询依然缺少传感器服务则报告失败，不跳过检查。
2. 有连接空位时不轮换正常设备。已满时，只有等待设备已满足新广播条件才释放一台完成窗口的设备。未发现的设备触发扫描，持续失败的设备逐台退避。
3. 正常关闭后至少 5 秒及新的广播才可连接。首条有效样本才重置失败计数，BLE 连接成功不能代替数据有效。
4. 仅取消已成功订阅的通知。失败会话若释放失败，保留对象并禁止该 MAC 建立新会话，30 秒后重新清理；其他 MAC 的采集不被长期锁住。退出时再次尝试释放。扫描启动和停止各有 10 秒等待上限。
5. 诊断保留查询方式、阶段、代次、耗时、明确等待秒数及清理状态。

实现只使用 Bleak 公共连接 API，未直接改写其 WinRT 私有状态。完整/定向服务枚举与非缓存参数依据 [Bleak Windows 文档](https://bleak.readthedocs.io/en/latest/backends/windows.html) 和 [WinRT 后端源码](https://github.com/hbldh/bleak/blob/v3.0.2/bleak/backends/winrt/client.py)。上述策略是针对日志证据的恢复措施，不能保证消除驱动或无线环境本身的问题。
